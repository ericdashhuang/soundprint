# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Two services: `backend/` (FastAPI + SQLModel/Postgres) and `frontend/` (Next.js App Router). See the root `README.md` for how to run both locally. Deployment target is Render, via the `render.yaml` Blueprint at the repo root - see `DEPLOYMENT.md` for the remaining manual setup steps.
- `backend/app/database.py`'s `get_engine()` rewrites a bare `postgres://`/`postgresql://` `DATABASE_URL` to the `postgresql+psycopg://` dialect before calling `create_engine`. This isn't cosmetic: only `psycopg` (v3) is in `requirements.txt`, not `psycopg2`, and SQLAlchemy's default dialect for an unprefixed `postgresql://` URL is psycopg2 - without the rewrite, connecting to a real Postgres (e.g. Render's managed database, whose `fromDatabase`-supplied connection string is a bare `postgresql://` URL) raises `ModuleNotFoundError: No module named 'psycopg2'` the first time the app touches the database. Verified live against a local Postgres 16 instance (not just SQLite) - see `backend/tests/test_database.py`.
- Render's blueprint `fromService` env var reference only exposes a service's private-network host/port, never its public URL - confirmed against Render's own blueprint-spec docs. `render.yaml` therefore hardcodes each web service's public `https://<name>.onrender.com` URL for `CORS_ORIGINS` / `NEXT_PUBLIC_API_BASE_URL` rather than templating them; renaming either service or adding a custom domain means updating both values by hand (noted in `render.yaml` and `DEPLOYMENT.md`).
- There is no user auth anywhere in this product. Spotify access is server-side only, via the Client Credentials flow (app-level token, no login) in `backend/app/spotify_client.py`. This was a deliberate captain decision: Spotify's Development Mode caps a new app at 5 logged-in users with no realistic path to more for a solo project, so personalized login was dropped entirely.
- Spotify's `audio-features`/`audio-analysis` endpoints are gone for any app registered after 2024-11-27. There is no first-party energy/valence/danceability data available, and `preview_url` is frequently null/unpredictable per track - real-world testing across several major albums found zero available preview clips, so treat preview availability as the exception, not the norm.
- The per-track vibe pipeline (`backend/app/vibe_service.py`) tries three sources in order: cache -> ReccoBeats (`backend/app/reccobeats_client.py`, keyed by Spotify track ID, no audio needed) -> preview+librosa (`backend/app/vibe_analysis.py`) -> `None`. ReccoBeats is primary precisely because preview clips are now rarely available; librosa remains only as a fallback for tracks ReccoBeats has no data for. See `reccobeats_client.py`'s docstring for the confirmed API contract (base URL, no-auth-required, field mapping) and `vibe_analysis.py`'s docstring for why Essentia's pretrained mood classifiers weren't used for the fallback (no model weights ship with the pip package; running them needs a separate runtime download this repo doesn't vendor). Beyond the original energy/brightness(valence)/tempo, ReccoBeats-sourced rows also carry danceability/acousticness/instrumentalness/speechiness/loudness/key/mode (used by the guessing game's hint reveal - see below); the librosa fallback has no equivalent for these, so they're `None` on `source == "librosa_fallback"` rows. Results are cached in Postgres by Spotify track ID (`TrackVibe` model, whose `source` column traces which pipeline produced a row) so a track is only ever computed once, even across different albums/playlists/rounds. A track with no data from either source gets `vibe: null` rather than failing the request.
- Backend tests never call the real Spotify or ReccoBeats APIs - they mock `httpx` calls with `respx` (see `backend/tests/`). Keep it that way; live credentials should never be required to run the test suite. Vibe-pipeline tests likewise mock `get_track_vibe`/`download_preview_clip`/`analyze_audio` rather than hitting the network; `backend/tests/fixtures/tiny_clip.wav` is a tiny checked-in fixture for the one test that runs real librosa analysis.
- The product is an artist album-guessing game (not a paste-a-link lookup tool - that mode was fully removed). `backend/app/game_service.py` orchestrates it server-side: resolves an artist (by name search or by exact Spotify ID, the latter used by the frontend's autocomplete to avoid same-name-artist ambiguity), picks a secret target album (rerolling on sparse vibe data), and holds all round state - including the target's identity, track names, and the cumulative list of wrong-guessed (eliminated) album IDs - in the `GameRound` table (`backend/app/models.py`) until a round is solved or given up. Elimination state is server-authoritative and returned in full on every guess response (`GuessResponse.eliminated_album_ids`); the frontend renders from that list rather than accumulating its own, precisely because a previous frontend-only-tracking design had a reported bug there. The `/api/game/rounds*` and `/api/game/artists` endpoints in `backend/app/main.py` are the only access path; no in-progress-round response may ever include the target's identity or a track name - see the tests in `backend/tests/test_game_endpoint.py` that assert this directly against real HTTP responses. Studio-album filtering (`_looks_like_non_studio_edition` / `_filter_out_albums_with_non_studio_tracks` / `_dedupe_albums_by_base_name` in `game_service.py`) is a name-pattern heuristic, not a perfect classifier - Spotify's `album_type=album` filter alone still lets live albums, remixes, and deluxe/anniversary/reissue editions through. It checks both the album's own name *and* its track names against the same pattern list, since some editions give no hint in the album title itself - confirmed live for Radiohead's "I Might Be Wrong" (a live album; every track says "- Live in <city>", but the title doesn't) and "OK Computer OKNOTOK 1997 2017" (an anniversary reissue whose tracks say "- Remastered", not "anniversary"). The track-name check fetches every remaining candidate's tracklist concurrently (`asyncio.gather`), same reasoning as the vibe-lookup fix below - don't turn this into a sequential per-album loop.
- Round-start fetches vibe data via `vibe_service.get_or_compute_vibes_bulk`, not a per-track loop over `get_or_compute_vibe`. This matters: looping the single-track lookup once serialized what can be dozens of ReccoBeats round trips (a round can need vibe data for up to 3 candidate albums if rerolling) into a request that took ~16s on a cold cache - long enough to look permanently hung to an end user (and to an automated check that didn't wait it out), even though the backend was working correctly the whole time. The bulk helper keeps DB reads/writes sequential (SQLAlchemy's sync `Session` isn't safe for concurrent use) but runs the actual network calls concurrently via `asyncio.gather`, cutting that to ~2s regardless of track count. If round-start ever feels slow again, check whether something reintroduced a per-track sequential await instead of using the bulk path.
- The frontend chart (`frontend/app/GameChart.tsx`) shows one metric's line at a time via a toggle control (not overlaid lines) - a wider, horizontally-scrollable chart with per-point spacing so each point's "Track N" x-axis label and (post-reveal) truncated track title both fit. `frontend/app/MetricGlossary.tsx` always lists every metric's plain-language description from round start, dimming ones not yet unlocked - it's shared between the round and reveal states rather than being reveal-only.
- Spotify's `GET /artists/{id}/albums` endpoint rejects `limit` above 10 with a 400 "Invalid limit" - confirmed live, despite docs suggesting up to 50. `SpotifyClient.get_artist_albums` (`backend/app/spotify_client.py`) pages through the response's `next` link to still collect an artist's full studio catalog. Re-check this ceiling if Spotify ever changes it back.
- `CORSMiddleware` in `backend/app/main.py` lists `allow_methods` explicitly (currently `["GET", "POST"]`) - any new endpoint using a method not in that list will fail purely at the browser's CORS preflight, not at the route itself, which is easy to misdiagnose as a backend bug.
- `SpotifyClient` (`backend/app/spotify_client.py`) is the single place Spotify HTTP requests are made (`_get_with_retry`, routed through by both `_get` and `_get_absolute`) - it retries a 429 up to `_MAX_RATE_LIMIT_RETRIES` times, honoring `Retry-After` (capped at `_MAX_RATE_LIMIT_BACKOFF_SECONDS`, since Spotify can return a `Retry-After` in the tens of thousands of seconds for a request pattern it treats as abusive - confirmed live). Any new code that needs to call Spotify should go through a `SpotifyClient` method rather than making a raw `httpx` call, so it gets this retry behavior for free. Confirmed live: firing an unbounded `asyncio.gather` burst of Spotify requests (one per item in a collection, e.g. `game_service._filter_out_albums_with_non_studio_tracks`'s original per-album tracklist fetch) is enough on its own to trip Spotify's real short-window rate limit, deterministically, on every call - not a flaky or time-based issue. Any new bulk/fan-out Spotify call must cap its concurrency (e.g. an `asyncio.Semaphore`, see `_MAX_CONCURRENT_ALBUM_TRACK_FETCHES` in `game_service.py`) rather than firing every request via a single unbounded `gather` - while still keeping the calls concurrent rather than serializing them (see the vibe-lookup note above on why sequential per-item awaits are also wrong).
- `backend/app/main.py`'s lifespan startup hook eagerly warms outbound connections (`backend/app/warmup.py`) after `init_db()`: it makes a real Spotify search (which also fetches the client-credentials token) and a real ReccoBeats lookup before the app accepts traffic. This exists because a fresh process pays a one-time connection tax (DNS/TLS to each third-party host) on whichever request happens to hit that host first, then every later request in the same process is fast - without warm-up this showed up as a slow first artist-autocomplete and a slow first round-start after every Render cold start, even once Render's own spin-up delay had resolved. `Settings.warm_up_on_startup` (default `True`) gates it off in tests via `backend/tests/conftest.py` (`WARM_UP_ON_STARTUP=false`), since the suite must never make a real Spotify/ReccoBeats call - see `backend/tests/test_warmup.py` for the respx-mocked coverage instead.
- The backend test suite runs against an in-memory SQLite engine (`DATABASE_URL=sqlite:///:memory:`, set in `backend/tests/conftest.py`), not Postgres. `backend/app/database.py`'s `get_engine()` special-cases in-memory SQLite URLs to use a shared `StaticPool` connection.
- Frontend tests use Vitest + React Testing Library (jsdom), run with `npm test` from `frontend/`. Config is `frontend/vitest.config.mts` / `frontend/vitest.setup.ts`. The setup file polyfills `ResizeObserver` and stubs `HTMLElement` offset dimensions (both needed for Recharts' `ResponsiveContainer` to render in jsdom), and calls RTL's `cleanup()` after each test (not automatic under Vitest). `frontend/app/types.ts` must be kept in sync with `backend/app/schemas.py` by hand - nothing enforces this across the language boundary. `frontend/app/page.test.tsx` mocks `frontend/app/api.ts` (not `fetch` directly) to drive the game's landing/round/reveal states - there's no `user-event` package installed, so tests use RTL's `fireEvent`.
